Introduction

Purpose

Our testing strategy primarily existed as hosting a series of smaller testing periods every time that a new part of the project was implemented in the user interface. This testing process included testing multiple cases from the new implemented portion as well as additional testing to ensure that the new part of the code didn’t break what was already there before each testing session. If anything ended up breaking or otherwise not working as intended, the group would return to iron out the mistakes and test again.

Project Overview

The project was a Degree Admin database that would allow students, faculty, and administrators to view and update different aspects of their school accounts. These aspects included schedules, majors and minors, passwords, and co-op opportunities. Each one of these areas needed to be developed and tested separately, and user login needed to ensure that each different type of user would be interacting with a different interface with different levels of permissions once a successful login occurred.

Scope

In-Scope

As mentioned in section 1.2, there are many parts of the project that will be tested by our group members. The login interface and redirections to different user homepages is the first priority. After that, allowing the user to change their password according to the password specifications (12 characters, at least one uppercase letter, at least one lowercase letter, at least one number, and at least one special character). The next priority will be checking to see whether administrators can add or remove courses from the available courses catalog, as well as test their ability to change any person’s username and password. Co-op requests as well as Major/Minor change requests need to be tested on both student and faculty levels as well. Profile information must be displayed on each user type’s profiles, and faculty members need to be able to view their advisees. Faculty members and administrators need to be able to change course requirements for a major or minor, and administrators need to have the ability to add or delete users and reassign advisors and advisees.

Out-of-Scope

Due to the time constraints and our inability to complete some portions of the project, we will not be able to test a multi-semester schedule implementation. Likewise, we will not be testing course prerequisite requirements, even if they are present in the project’s database.

Testing Strategy

Test Objectives

Each testing piece within our scope must be tested, both on their own as well as in tandem with the other pieces. Tests should ensure that implementing a new piece doesn’t cause previous pieces to stop working as intended.

Test Assumptions

This project assumes that a student user has taken any prerequisite courses required for the courses they are actively taking. To mitigate this, we are making sure that students don’t register for a course and its prerequisite at the same time. We will operate with those ideas in mind, and we will continue on as planned.

Data Approach

We will approach this data from all relevant user types’ perspectives. For example, the co-op request testing will require testing for a student user as well as a faculty member perspective. Another example is the user login. We must test the login procedure from a student, faculty, and administrator point of view to ensure that each type is taken to the correct profile page.

Environment Requirements

Test Environments

  • MYSQL and Apache for php are required to run the project
  • The database is hosted locally on the tester’s device and opened through an internet window.
  • MYSQL file setup.sql must be reloaded into the database before any internet window is opened.

Dependencies

Any project testing wholly depended on whether the required php or MYSQL worked at that moment on each team member’s devices. There were many instances where a different group member needed to take up someone else’s testing due to the original member’s computer not registering the programs. This combined with the deadline and busy schedules to see the project testing perhaps not be as efficient as it could have been.
