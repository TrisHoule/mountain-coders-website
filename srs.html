1. Introduction

1.1 Purpose

The purpose of this Software Requirements Specification is to define the functional and non-functional requirements for DegreeAdmin, a web based academic planning system. This document describes the intended behavior of the system, its users, system features, constraints, and requirements.

DegreeAdmin is designed to help students, faculty, and admins manage degree progress, academic requirements, course planning, and co-op requests in a centralized system.

1.2 Scope

DegreeAdmin provides a digital platform for managing academic planning. The system allows students to view and manage majors, minors, course requirements, prerequisites, enrollments, and co-op requests. Faculty users can advise students and approve said co-op requests. Administrative users can manage courses, accounts, and advising relationships.

The current system includes authentication, user role handling, co-op request management, faculty-student advising relationships, course enrollments, major and minor requirement tracking, and prerequisite relationships. Future versions are expected to implement improved scheduling, course visualization, administrative features, and improvements to the overall interface.

1.3 Project Overview

DegreeAdmin is intended to reduce confusion in academic planning. Students often struggle to understand complex degree requirements, especially when managing multiple majors or minors. They may also have difficulty determining prerequisites, course availability, schedule conflicts, and whether they are on track to graduate on time. Faculty advising can also become time-consuming and inconsistent when handled manually.

DegreeAdmin addresses these issues by providing a structured web application where users can access degree information, track requirements, submit requests, and manage academic relationships.

2. Overall Description

2.1 Product Perspective

DegreeAdmin is a standalone web application built using PHP, MySQL, and CSS. The system uses a database to store user information, courses, majors, minors, prerequisites, enrollments, advising assignments, and co-op requests.

The system is role-based. When users log in, they are redirected to a dashboard based on their assigned role: student, faculty, or system administrator.

2.2 Product Functions

  1. User authentication
  2. Role-based dashboards
  3. Student profile viewing
  4. Password changing
  5. Major and minor requirement tracking
  6. Course prerequisite tracking
  7. Faculty advising assignments
  8. Student course enrollment tracking
  9. Student co-op request submission
  10. Faculty co-op approval or denial
  11. Administrative course and account management

2.3 User Classes and Characteristics

2.3.1 Student Users

Student users are the primary users of the academic planning service. They need access to their degree information, majors, minors, course requirements, schedules, enrollments, and co-op requests.

Student users shall be able to:

  • View profile information
  • View selected majors and minors
  • View required courses for majors and minors
  • Submit co-op requests
  • View co-op request statuses
  • View schedule or enrollment information
  • Change their password

2.3.2 Faculty Users

Faculty users are responsible for advising students and reviewing student requests.

Faculty users shall be able to:

  • View assigned advisees
  • View student academic information
  • Approve or deny co-op requests
  • Provide guidance to students
  • Change their password

2.3.3 Administrative Users

Administrative users manage the system’s academic and user data.

Admin users shall be able to:

  • Add courses
  • Delete courses
  • Manage user accounts
  • Remove accounts
  • Assign faculty and students to each other
  • Access administrative dashboard functions

2.4 Operating Environment

The system shall operate in a web browser environment.

Expected environment:

  • Frontend: HTML/CSS
  • Backend: PHP
  • Database: MySQL
  • Browser: Any modern web browser (Chrome, Firefox, Edge, etc)
  • Server: Local or hosted web server capable of running PHP and MySQL

2.5 Design and Implementation Constraints

The system shall be implemented using:

  • PHP for server-side page logic
  • MySQL for database storage
  • CSS for visual flair

Some constraints are:

  • Users must be authenticated before accessing role-specific pages
  • User permissions must be based on role
  • Database relationships must preserve academic data integrity
  • Password validation must follow the system’s password rules

2.6 Assumptions and Dependencies

The system assumes:

  • Users already exist in the database or are created by the administrator
  • Course, major, minor, and prerequisite data are entered into the database
  • Each user has one assigned role
  • Students may have multiple majors or minors
  • Faculty may advise multiple students
  • Co-op requests are reviewed by faculty users
  • The application depends on a functioning MySQL database and PHP server.

3. External Interface Requirements

3.1 User Interface Requirements

The system shall provide web pages for:

  • Login
  • Logout
  • Student dashboard
  • Faculty dashboard
  • Admin dashboard
  • Profile information
  • Password change
  • Co-op request submission
  • Co-op request review

No special hardware required. Users shall access the system through a device capable of running a web browser, such as:

  • Desktop computer
  • Laptop
  • Tablet

3.3 Software Interface Requirements

The system shall interact with:

  • A MySQL database
  • PHP server-side scripts
  • Browser-based HTML/CSS pages

The database shall store information for:

  • Users
  • Students
  • Faculty
  • System administrators
  • Courses
  • Majors
  • Minors
  • Major requirements
  • Minor requirements
  • Course prerequisites
  • Enrollments
  • Advising assignments
  • Co-op requests

3.4 Communication Interface Requirements

The system shall use standard web communication between the client browser and the server. Database communication shall occur between PHP scripts and the MySQL database.

4. System Features and Functional Requirements

4.1 Authentication and Login

Description

The system shall allow users to log in using a username and password. After successful authentication, users shall be redirected to the correct dashboard based on their role.

Functional Requirements

FR-1: The system shall provide a login page.

FR-2: The system shall require users to enter a username and password.

FR-3: The system shall validate entered credentials against stored user records

FR-4: The system shall display an error message when credentials are invalid.

FR-5: The system shall create a session when login is successful.

FR-6: The system shall redirect student users to the student dashboard.

FR-7: The system shall direct faculty users to the faculty dashboard.

FR-8: The system shall redirect administrative users to the administrator dashboard.

4.2 Logout

Description

The system shall allow users to securely log out of their account.

Functional Requirements

FR-9: The system shall provide a logout option

FR-10: The system shall destroy the user session when logout is selected.

FR-11: The system shall redirect users to the login page after logout.

FR-12: The system shall prevent logged-out users from accessing protected pages.

4.3 Password Change

Description

The system shall allow users to change their password from their profile page.

Functional Requirements

FR-13: The system shall provide a change password page.

FR-14: The system shall require the user to enter the current password.

FR-15: The system shall verify that the current password matches the stored password.

FR-16: The system shall require the user to enter a new password.

FR-17: The system shall require the user to confirm the new password.

FR-18: The system shall verify that the new password and confirmation match.

FR-19: The system shall enforce password rules.

FR-20: The system shall update the password when all validation checks pass.

FR-21: The system shall display an error message when password validation fails.

To note as well, passwords must be exactly 12 characters and include uppercase, lowercase, numbers and symbols.

4.4 Student Profile

Description

The system shall allow student users to view their personal academic information.

Functional Requirements

FR-22: The system shall display the student’s full name.

FR-23: The system shall display the student’s username.

FR-24: The system shall display the student’s role.

FR-25: The system shall display the student’s assigned faculty advisor.

FR-26: The system shall display the student’s majors.

FR-27: The system shall display the student’s minors.

FR-28: The system shall provide access to the change password page from the profile page.

4.5 Major and Minor Management

Description

The system shall support students having multiple majors and minors. Each major and minor shall be linked to its required courses.

Functional Requirements

FR-29: The system shall store major information.

FR-30: The system shall store minor information.

FR-31: The system shall associate students with one or more majors.

FR-32: The system shall associate students with one or more minors.

FR-33: The system shall link each major to required courses.

FR-34: The system shall link each minor to required courses.

FR-35: The system shall allow students to view courses required by their selected majors.

FR-36: The system shall allow students to view courses required by their selected minors.

To note, major requirements and minor requirements link each major or minor to the specific courses required for completion.

4.6 Course Prerequisites

Description

The system shall maintain prerequisite relationships between courses.

Functional Requirements

FR-37: The system shall store course information.

FR-38: The system shall store prerequisite relationships between courses.

FR-39: The system shall allow users to view prerequisite requirements for courses.

FR-40: The system shall prevent inaccurate prerequisite relationships by maintaining database references between course records.

To note, course prerequisites are links between each course and the course that must be taken before it.

4.7 Advising Relationships

Description

The system shall connect faculty advisors to the students they advise.

Functional Requirements

FR-41: The system shall store faculty records.

FR-42: The system shall store student records.

FR-43: The system shall associate students with faculty advisors.

FR-44: The system shall allow faculty to view assigned advisees.

FR-45: The system shall allow students to view their assigned advisor.

To note, the advising/enrollment system connects faculty to the students they advise.

4.8 Student Course Enrollments

Description

The system shall connect students to courses they are taking.

Functional Requirements

FR-46: The system shall store course offering information.

FR-47: The system shall associate students with course offerings.

FR-48: The system shall allow students to view current course enrollments.

FR-49: The system shall allow faculty or administrators to view student enrollment information where appropriate.

To note, enrollments connect students to the courses they take.

4.9 Co-op Request Submission

Description

Student users shall be able to submit co-op requests by selecting a semester and year.

Functional Requirements

FR-50: The system shall provide a co-op request form for students.

FR-51: The system shall require students to select a semester.

FR-52: The system shall require students to enter or select a year.

FR-53: The system shall submit the co-op request to the database.

FR-54: The system shall assign a default status of pending to new co-op requests.

FR-55: The system shall display the student’s submitted co-op requests.

FR-56: The system shall display the status of each co-op request.

4.10 Co-op Request Approval

Description

Faculty users shall be able to view student co-op requests and approve or deny pending requests.

Functional Requirements

FR-57: The system shall display co-op requests to faculty users.

FR-58: The system shall show the student, semester, year, and status of each co-op request.

FR-59: The system shall provide approve and deny actions for pending requests.

FR-60: The system shall update the co-op request status when approved.

FR-61: The system shall update the co-op request status when denied.

FR-62: The system shall prevent further action on requests that are already approved or denied.

4.11 Administrator Course Management

Description

Administrator users shall be able to manage course information.

Functional Requirements

FR-63: The system shall allow administrators to add courses.

FR-64: The system shall allow administrators to delete courses.

FR-65: The system shall allow administrators to edit course-related information where implemented.

FR-66: The system shall restrict course management functions to administrator users.

To note, adding and deleting courses is an administrator ability.

4.12 Administrator User Management

Description

Administrator users shall be able to manage accounts and relationships between students and faculty.

Functional Requirements

FR-67: The system shall allow administrators to remove accounts.

FR-68: The system shall allow administrators to assign faculty to students.

FR-69: The system shall allow administrators to manage student-faculty advising relationships.

FR-70: The system shall restrict account management functions to administrator users.

4.13 Schedule Planning

Description

The system supports semester-by-semester schedule planning.

Functional Requirements

FR-71: The system should allow students to build semester schedules.

FR-72: The system should allow students to view schedules by semester or year.

FR-73: The system should check whether planned courses satisfy major or minor requirements.

FR-74: The system should identify prerequisite issues in planned schedules.

FR-75: The system should help students determine whether they are on track to graduate.

5. Non-Functional Requirements

5.1 Performance Requirements

NFR-1: The system should load standard pages within 2 seconds under normal use.

NFR-2: The system should process login requests within 2 seconds.

NFR-3: The system should retrieve student, course, and co-op data efficiently from the database.

NFR-4: The system should support multiple users accessing the system at the same time.

5.2 Security Requirements

NFR-5: The system shall require authentication before accessing protected pages.

NFR-6: The system shall use role-based access control.

NFR-7: Students shall not access administrator-only pages.

NFR-8: Faculty shall not access administrator-only pages.

NFR-9: Users shall only access functions appropriate to their assigned role.

NFR-10: The system shall validate password changes before updating stored credentials.

NFR-11: The system shall end user sessions when users log out.

NFR-12: The system should protect database operations from unauthorized access.

5.3 Usability Requirements

NFR-13: The interface shall be simple and understandable for students, faculty, and administrators.

NFR-14: Each user role shall have a clear dashboard.

NFR-15: Buttons and navigation links shall clearly describe their actions.

NFR-16: Error messages shall clearly explain what went wrong.

NFR-17: Success messages shall confirm completed actions.

5.4 Reliability Requirements

NFR-18: The system shall preserve user, course, and request data in the database.

NFR-19: The system shall prevent invalid database relationships where possible.

NFR-20: The system shall maintain accurate co-op request statuses.

NFR-21: The system shall prevent broken advising or enrollment relationships.

5.5 Maintainability Requirements

NFR-22: The system code should be organized into separate PHP pages based on function.

NFR-23: CSS should be stored separately from PHP logic.

NFR-24: Database tables should use clear relationships and primary/foreign keys.

NFR-25: The system should be documented so future developers can continue implementation.

5.6 Portability Requirements

NFR-26: The system should run on any server environment that supports PHP and MySQL.

NFR-27: The system should be accessible from modern web browsers.

7. Use Cases

7.1 Use Case: User Logs In

Actor: Student, Faculty, or Admin

Precondition: User has an account.

Main Flow:

  1. User opens the login page.
  2. User enters username and password.
  3. System validates credentials.
  4. System identifies user role.
  5. System redirects user to the correct dashboard.

Postcondition: User is logged into the system.

Alternate Flow: If the credentials are invalid, an error message pops.

7.2 Use Case: Student Submits Co-op Request

Actor: Student

Precondition: Student is logged in.

Main Flow:

  1. Student opens the co-op request page.
  2. Student selects semester.
  3. Student enters year.
  4. Student submits the request.
  5. System stores the request with pending status.
  6. System displays the request in the student’s request list.

Postcondition: Co-op request is stored and ready for faculty view.

7.3 Use Case: Faculty Reviews Co-op Request

Actor: Faculty

Precondition: Faculty is logged in.

Main Flow:

  1. Faculty opens the co-op request page.
  2. System displays pending requests.
  3. Faculty selects approve or deny.
  4. System updates the request status.

Postcondition: Student request status is updated.

7.4 Use Case: Student Views Degree Requirements

Actor: Student

Precondition: Student is logged in and has selected majors/minors.

Main Flow:

  1. Student opens course or requirement view.
  2. System retrieves selected majors and minors.
  3. System retrieves required courses.
  4. System displays required courses to the student.

Postcondition: Student can view required academic coursework.

7.5 Use Case: Administrator Assigns Advisor

Actor: Administrator

Precondition: Admin is logged in.

Main Flow:

  1. Admin opens advising management page.
  2. Admin selects a student.
  3. Admin selects a faculty member.
  4. System saves the advising relationship.

Postcondition: Student is assigned to a faculty advisor.

8. Data Validation Requirements

DVR-1: Username and password fields shall not be empty during login.

DVR-2: Co-op request semester shall not be empty.

DVR-3: Co-op request year shall not be empty.

DVR-4: New passwords shall match confirmation passwords.

DVR-5: New passwords shall meet system password rules.

DVR-6: Course relationships shall reference valid course records.

DVR-7: Major requirement records shall reference valid major and course records.

DVR-8: Minor requirement records shall reference valid minor and course records.

DVR-9: Co-op request statuses shall be limited to valid values such as pending, approved, or denied.
